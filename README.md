# Hogwarts Quidditch

Готовое статическое веб-приложение для проведения матчей по квиддичу в текстовой ролевой игре.

## Структура

```text
Hogwarts-Quidditch/
├── index.html
├── player-login.html
├── judge-login.html
├── player.html
├── judge.html
├── screen.html
├── css/
│   └── style.css
├── js/
│   ├── supabase.js
│   ├── auth.js
│   ├── player-login.js
│   ├── judge-login.js
│   ├── player.js
│   ├── judge.js
│   ├── screen.js
│   ├── chat.js
│   └── snitch.js
└── sql/
    └── setup.sql
```

Node.js, npm и сборщик не нужны.

---

# 1. Создайте Supabase

1. Откройте https://supabase.com/
2. Создайте новый проект.
3. Дождитесь окончания запуска проекта.
4. Откройте **SQL Editor**.
5. Создайте новый SQL-запрос.
6. Полностью скопируйте содержимое `sql/setup.sql`.
7. Нажмите **Run**.

Скрипт создаёт таблицы, RLS-политики, RPC-функции, Storage bucket `snitch-catches` и подключение таблиц к Supabase Realtime.

## Если SQL выполняется повторно

Основные `create table` и функции написаны так, чтобы файл можно было запускать повторно. Если вы уже меняли старую схему проекта вручную, сначала сделайте резервную копию данных.

# 2. Где взять Project URL и Publishable/anon key

В Supabase откройте:

**Project Settings → API**

Найдите:

- Project URL
- Publishable key

В старых проектах вместо Publishable key может отображаться anon key. Для этого приложения подходит publishable/anon ключ.

Откройте:

```text
js/supabase.js
```

В начале файла находятся две строки:

```js
const SUPABASE_URL = "https://YOUR-PROJECT.supabase.co";
const SUPABASE_ANON_KEY = "YOUR_PUBLISHABLE_OR_ANON_KEY";
```

Замените значения на данные своего проекта.

**Никогда не вставляйте сюда service_role key.**

---

# 3. Почему в проекте нет jsDelivr

Приложение не зависит от `@supabase/supabase-js` и не загружает JavaScript-библиотеку через jsDelivr.

`js/supabase.js` использует:

- обычный HTTPS REST API Supabase;
- Supabase Storage API;
- Supabase Realtime WebSocket.

Поэтому для фронтенда не требуется внешний JavaScript SDK.

# 4. Создание первого судьи

После выполнения `setup.sql` откройте SQL Editor и выполните:

```sql
insert into public.users(username,password_hash,display_name,role)
values (
  'judge',
  crypt('CHANGE-ME', gen_salt('bf',12)),
  'Главный судья',
  'judge'
);
```

Перед запуском замените `CHANGE-ME` на свой пароль.

Например:

```sql
insert into public.users(username,password_hash,display_name,role)
values (
  'judge',
  crypt('МойНадёжныйПароль', gen_salt('bf',12)),
  'Главный судья',
  'judge'
);
```

После создания судьи можно входить через:

```text
judge-login.html
```

# 5. Создание игроков

В SQL Editor можно создать игрока:

```sql
insert into public.users(username,password_hash,display_name,role)
values (
  'player1',
  crypt('ПарольИгрока', gen_salt('bf',12)),
  'Имя игрока',
  'player'
);
```

Капитана:

```sql
insert into public.users(username,password_hash,display_name,role)
values (
  'captain1',
  crypt('ПарольКапитана', gen_salt('bf',12)),
  'Имя капитана',
  'captain'
);
```

После этого игрок входит через `player-login.html`.

Судей и администраторов лучше создавать только администратору:

```sql
insert into public.users(username,password_hash,display_name,role)
values (
  'admin',
  crypt('ПарольАдмина', gen_salt('bf',12)),
  'Администратор',
  'admin'
);
```

# 6. Как создать матч

1. Откройте `judge-login.html`.
2. Войдите под судьёй.
3. В разделе **Создать матч** укажите:
   - название матча;
   - название команды 1;
   - название команды 2.
4. Нажмите **Создать матч**.
5. Выберите созданный матч в списке.

Команды не связаны с факультетами Hogwarts и могут называться как угодно.

---

# 7. Как добавить игроков

В выбранном матче судья видит блок **Игроки**.

Выберите:

1. пользователя;
2. команду;
3. позицию:
   - Вратарь;
   - Ловец;
   - Загонщик;
   - Охотник.

Нажмите **Добавить игрока**.

Один пользователь не может быть дважды назначен в один матч.

---

# 8. Как начать матч

В панели судьи доступны:

- Запустить матч;
- Пауза;
- Продолжить;
- Завершить матч;
- Этап 1;
- Этап 2;
- Этап 3.

После запуска статус становится `stage_1`.

При паузе статус становится `paused`.

После продолжения приложение возвращает матч на текущий этап.

---

# 9. Как работает игрок

Игрок входит через `player-login.html`.

В кабинете он видит:

- своё имя;
- команду;
- позицию;
- название матча;
- очки своей команды;
- очки соперника;
- статус матча;
- текущий этап;
- вопросы;
- ответы;
- чат.

Игрок может отправлять вопросы и ответы через RPC.

Ответ на собственный вопрос отправить нельзя.

---

# 10. Ловец и снитч

Если игрок имеет позицию `seeker`, появляется блок:

**Ловец**

Ловец:

1. нажимает выбор файла;
2. выбирает JPG/JPEG/PNG/WEBP;
3. размер файла не должен превышать 10 МБ;
4. получает предпросмотр;
5. нажимает **Подтвердить поимку**.

Фотография загружается в bucket:

```text
snitch-catches
```

После этого создаётся заявка со статусом:

```text
pending
```

Матч автоматически не завершается.

---

# 11. Проверка снитча судьёй

Судья видит раздел **Поимки снитча**.

Для каждой заявки доступны:

- фотография;
- имя ловца;
- команда;
- дата;
- статус;
- Подтвердить;
- Отклонить.

При подтверждении PostgreSQL выполняет одну атомарную транзакцию:

1. заявка переводится в `approved`;
2. записывается `approved_at`;
3. команде добавляется **150 очков**;
4. матч переводится в `finished`.

Повторно подтвердить ту же заявку нельзя.

При отклонении статус становится `rejected`, а матч продолжается.

# 13. Realtime

Приложение подключается к Supabase Realtime через WebSocket.

Подписки настроены на:

- `matches`;
- `teams`;
- `questions`;
- `answers`;
- `chat_messages`;
- `snitch_catches`.

При изменении данных страницы обновляют соответствующие блоки без ручной перезагрузки.

Если соединение WebSocket временно оборвалось, клиент пытается подключиться снова.

# 14. Storage

SQL автоматически создаёт bucket:

```text
snitch-catches
```

Bucket используется для фотографий снитча.

В браузер не помещается `service_role`.

---

# 15. RLS и безопасность

Для игровых данных включён RLS.

Публичный экран должен иметь возможность читать:

- matches;
- teams;
- questions;
- answers;
- chat_messages;
- snitch_catches.

Поэтому эти таблицы доступны для чтения.

Изменения игровых данных напрямую из браузера запрещены. Важные операции проходят через `SECURITY DEFINER` RPC:

- создание матча;
- запуск;
- пауза;
- продолжение;
- завершение;
- назначение игроков;
- вопросы;
- ответы;
- оценка;
- чат;
- заявка на снитч;
- подтверждение снитча.

Особенно важная функция `approve_snitch` блокирует запись и одновременно меняет заявку, очки и статус матча.

# 16. Ограничение собственной авторизации

Здесь намеренно используется собственная таблица `users`, потому что это было предусмотрено техническим заданием.

Пароли не хранятся открытым текстом: используется `pgcrypto` и bcrypt через `crypt()`.

После входа браузер получает случайный токен сессии. В базе хранится только SHA-256 hash токена.

Однако это всё равно не является полноценной заменой Supabase Auth.

Для публичного коммерческого сервиса с большим количеством пользователей рекомендуется перейти на:

- Supabase Auth;
- JWT;
- RLS с `auth.uid()`;
- приватные Storage policies.

Для ролевой игры с ограниченным кругом участников текущая схема значительно безопаснее простого хранения `username/password` в `localStorage`.

# 20. Типичный сценарий матча

1. Администратор создаёт аккаунты.
2. Судья входит в панель.
3. Судья создаёт матч.
4. Судья создаёт две команды через форму матча.
5. Судья добавляет игроков.
6. Игроки входят в свои аккаунты.
7. Судья запускает матч.
8. Игроки отправляют вопросы.
9. Другие игроки отправляют ответы.
10. Судья оценивает ответы.
11. Все участники используют чат.
12. Ловец загружает фотографию снитча.
13. Судья проверяет фотографию.
14. При подтверждении команда получает 150 очков.
15. Матч становится `finished`.
16. Публичный экран показывает сообщение «Снитч пойман!» и команду-победителя.
